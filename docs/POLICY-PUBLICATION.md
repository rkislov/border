# Черновики и публикация политик

В панели: **Конфигурация → Политики и доступ → Черновики и публикации**.
Редакторы авторизации, доступа и правил теперь сохраняют черновики. Существующие
рабочие политики при обновлении сервера остаются действующими.

1. Измените политику и сохраните черновик.
2. Откройте оценку влияния: сравнение полей, NAS с одиночной привязкой или
   набором политик, активные и потерянные сессии со связанным разрешением.
3. Опубликуйте проверенную редакцию. Изменение рабочей конфигурации, история,
   постановка разрешений на отзыв и удаление черновика выполняются атомарно.
4. Для отката выберите публикацию в истории. Создаётся черновик состояния
   **до выбранной публикации**, который снова нужно проверить и опубликовать.

Публикация изменённой политики отзывает все её ранее выданные разрешения,
включая сессии на NAS, с которых привязку уже сняли. Изменение авторизации
затрагивает разрешения всех ссылающихся политик доступа. Сессии других политик
того же пользователя сохраняются. Фоновый обработчик отправляет Disconnect
по существующей привязке разрешения и поколения сессии; результат, NAK и
повторные попытки видны в разделе сессий. Сам факт публикации не означает,
что NAS уже отключил пользователя. Поддержка Disconnect и доступность NAS
по-прежнему необходимы. Откат не снимает причины отзыва со старых разрешений:
пользователь должен войти снова.

Оценка — снимок зависимостей и существующих сессий, а не симуляция LDAP или
испытание оборудования. NAS показаны с учётом выключенных привязок. Несвязанные
сессии на этих NAS выводятся отдельно и автоматически не отключаются.
Количество сессий может измениться между просмотром и публикацией. Имена,
сроки, условия и прочие изменения обрабатываются консервативно: действующие
разрешения изменённой политики требуют повторной авторизации.

Для каждого вида и ID хранится один общий черновик текущей базы/тенанта.
Редакции монотонны даже после удаления и повторного создания. Старый запрос
не перезапишет новый черновик и не опубликует его. Изменение рабочей политики
после создания черновика блокирует публикацию: удалите устаревший черновик
и создайте его заново. Откат также не перезаписывает существующий черновик.
Первая публикация новой политики не имеет предыдущей версии: вместо удаления
можно опубликовать выключенное состояние. История в базе сохраняется целиком;
панель показывает последние 100 публикаций с автором и временем.

Сначала публикуйте новую политику авторизации, затем зависящую политику доступа,
после неё — правила. Пакетная публикация зависимых черновиков не реализована.
Изменение авторизации при публикации проверяет совместимость зависимых политик
доступа и правил. Привязки NAS, группы, сегменты и настройки LDAP пока сохраняются
по прежней схеме, без черновиков. Управление доступно только администраторам;
операторы и наблюдатели не имеют доступа к API черновиков и истории.

## API

- `GET /api/policy-drafts` — `Drafts`, `Releases`.
- `POST /api/policy-drafts` — `Kind` (`authentication`, `access`, `rules`),
  `PolicyID`, `Revision` (0 для создания), `Payload`.
- `GET /api/policy-drafts/impact?kind=access&id=example` — версия черновика,
  рабочая база, конфликт, устройства и две категории сессий.
- `POST /api/policy-drafts/publish` или `/discard` — `Kind`, `PolicyID`, `Revision`.
- `POST /api/policy-drafts/rollback` — `ReleaseID`.

Все изменения требуют CSRF. В тенанте используется обычный префикс `/t/<id>`.
Старые POST `/api/authentication-policies`, `/api/access-policies` и
`/api/access-rules` теперь создают черновик, а не публикуют изменения сразу.
Для изменения существующего черновика используйте версионированный API выше.

Проверки: изоляция черновиков, проверка зависимостей, атомарный отказ, конфликт
рабочей версии, одновременная публикация, защита от старого запроса после
пересоздания, версия правил при откате, избирательный отзыв связанных
разрешений, CSRF и запреты RBAC. Интерфейс проверен на изолированной базе:
сохранение → оценка → публикация → подготовка отката.
