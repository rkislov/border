# Резервное копирование и проверка восстановления

Команды `radiusd backup` входят в тот же бинарный файл Border. Дополнительные
программы для архивирования, SQLite или шифрования не нужны. Эта версия работает
с **SQLite**, включая отдельные базы всех тенантов. Для PostgreSQL нужен отдельный
план резервного копирования PostgreSQL; панель не позволяет включить этот механизм.

## Что сохраняется

- Корневая база и базы из её каталога `tenant_instances`. Используется
  [SQLite Online Backup API](https://www.sqlite.org/backup.html), включая записи WAL.
  Каждая база согласована отдельно; набор не является одной общей транзакцией
  всех тенантов. В манифесте записан интервал снятия снимков.
- Каталог конфигурации целиком: окружение с `BORDER_MASTER_KEY`, сертификаты,
  закрытые ключи и остальные обычные файлы. Секреты LDAP, SMTP, SMS, TOTP, CA,
  ACME, административной MFA и локального MS-CHAPv2 сохраняются вместе с соответствующими базами.
- Используемый бинарный файл и дополнительные файлы из `ExtraFiles` — например,
  systemd unit, его drop-in и конфигурация резервного копирования.

Каждый архив имеет SHA-256 файлов и зашифрован форматом
[age](https://pkg.go.dev/filippo.io/age) для отдельного X25519-ключа. Сам ключ age
**не включается в архив**, хранится вне каталогов-источников и хранилища копий.
Символические ссылки и специальные файлы в источниках запрещены. Изменение
конфигурации во время захвата прерывает операцию, чтобы не сохранить смешанные ключи.

Это резервная копия Border, а не всей машины. Данные внешнего AD/Samba, DNS,
FESS, NAS, Docker volumes и PostgreSQL требуют собственных копий. Если пути или
флаги службы изменены, администратор ОС должен обновить конфигурацию копирования.

## Установка службы

Сначала обновите бинарник и схему корневой БД до миграции 35. Типовая установка
под root, из каталога исходников/пакета развёртывания:

```sh
install -d -m 0700 /var/backups/border /var/lib/private/border-backup
install -d -o root -g border -m 0750 /var/cache/border-downloads
/usr/local/bin/radiusd backup init-key /var/lib/private/border-backup/identity.txt
install -m 0600 deploy/backup.example.json /etc/border-backup.json
install -m 0644 deploy/border-backup.service /etc/systemd/system/border-backup.service
install -m 0644 deploy/border-backup.timer /etc/systemd/system/border-backup.timer
systemctl daemon-reload
/usr/local/bin/radiusd backup run --config /etc/border-backup.json
systemctl enable --now border-backup.timer
```

`init-key` отказывается перезаписывать существующий ключ. `RootDB`, `TenantDir`,
`ConfigDir`, `EnvFile`, `CertDir`, `Binary`, `ExtraFiles`, `OutputDir` и `IdentityFile`
— абсолютные пути, задаваемые **только администратором ОС** в файле 0600.
`EnvFile` и `CertDir` должны находиться внутри `ConfigDir`. Ключ окружения должен
быть одной буквальной base64-строкой: подстановка команд и переменных не выполняется.
`MaxBytes` ограничивает суммарный распакованный размер; по умолчанию 4 GiB.
В хранилище нужно место для снимков, архива и отдельной распаковки проверки.
Если заданы `BORDER_DB` и `BORDER_TENANT_DIR`, используйте в них те же абсолютные
пути; несовпадение или `BORDER_DB_DRIVER=pgx` блокируют создание копии.
При других путях измените также `ReadWritePaths` в unit.

В корневой панели откройте **Конфигурация → Дополнительно → Резервные копии**.
Включите ежедневное расписание, выберите время, часовой пояс IANA и количество
сохраняемых проверенных копий (2–365, по умолчанию 14). Можно создать копию сейчас
и повторно проверить существующую. Администраторам тенантов, операторам и
наблюдателям этот API недоступен. Веб-сервер не получает доступ к ключу архива,
исходному хранилищу архивов или привилегированной конфигурации. Для скачивания
служба отдельно готовит проверенную зашифрованную копию, доступную веб-процессу
только для чтения.

Таймер проверяет очередь раз в минуту. При простое допускается один запуск за
текущую календарную дату с опозданием до 6 часов; накопленные дни не выполняются.
Несуществующее время при переходе на летнее время пропускается, повторное время
не создаёт второй копии за ту же дату. Заявки старше 6 часов помечаются просроченными.
Параллельный процесс блокируется файловой блокировкой ОС. После сбоя незавершённые
задания получают ошибку; если готовый архив уже был атомарно сохранён, служба
повторно проверяет его и восстанавливает успешный статус. Незавершённые временные
каталоги очищаются. Автоматический бесконечный повтор ошибочного задания отсутствует.

Очистка выполняется после успешного создания копии или доставки файла.
Архивы, ожидающие сетевой выгрузки, включая задания с ошибкой и приостановленные,
не удаляются до успешной доставки или явной отмены задания. Отключение выгрузки
не отменяет очередь; при длительной недоступности папки требуется контроль места.
Учитываются последние **N копий**, включая ручные; это не обещание хранения N дней.
Архивы с ошибкой повторной проверки не удаляются автоматически. После смены ключа
age старые архивы всё ещё требуют старый ключ: не удаляйте его до конца их хранения.

## Что означает успешная проверка

Архив расшифровывается и распаковывается в отдельный каталог 0700. Проверяются:

- Полная аутентификация потока, контрольные суммы, состав архива и безопасные пути.
- `PRAGMA integrity_check`, `foreign_key_check`, наличие схемы и всех тенантов
  из сохранённого корневого каталога.
- Расшифровка сохранённых секретов ключом из архивного окружения и производными
  ключами тенантов; соответствие управляемых CA их закрытым ключам.
- Соответствие bootstrap TLS-сертификатов ключам, читаемость CA и наличие бинарника.

Проверка не запускает RADIUS, фоновые публикации или уведомления и не обращается
к LDAP/NAS. Она не подтверждает сетевую доступность внешних сервисов, срок действия
или публичное доверие сертификатам. После настоящего восстановления нужны отдельные
проверки входа, LDAP, RADIUS и NAS. Текущая версия не делает инкрементальные копии.

История и отчёты доступны в панели, подробная причина ошибки — в журнале службы:

```sh
systemctl status border-backup.timer
journalctl -u border-backup.service
radiusd backup verify /path/backup-ID.tar.gz.age --key /secure/identity.txt
```

## Скачивание из панели

В `/etc/border-backup.json` задайте `"DownloadDir": "/var/cache/border-downloads"`.
В окружении основной службы добавьте `BORDER_BACKUP_DOWNLOAD_DIR=/var/cache/border-downloads`
и перезапустите Border. Каталог создаётся под root, группа совпадает с группой
корневой БД (`border`); права каталога 0750, файлов 0640. Родительский каталог
должен принадлежать root и не допускать запись других пользователей. Веб-процесс
не должен иметь права изменения этого каталога. При изменении пути обновите также
`ReadWritePaths` службы резервного копирования.

После очередного запуска таймера в истории появится доступная кнопка
**Подготовить скачивание**. Служба повторно проверит восстановление исходного
архива, скопирует его и сверит SHA-256 чтением готового файла. В очереди выгрузки
появятся ссылки **Скачать архив** и **Скачать SHA-256**, действующие один час.
Ссылки требуют входа администратором платформы; перед каждым скачиванием снова
проверяется SHA-256. Поддерживаются HTTP Range и продолжение загрузки; одновременно
допускаются две загрузки и до десяти подготовленных/ожидающих архивов.
После истечения часа временная копия удаляется следующим запуском службы.
Ключ age через веб-панель не передаётся. Сохраните его отдельно заранее.

## Автоматическое копирование в сетевую папку

Этот режим работает на Linux с уже подключённой NFS/SMB/SSHFS/rclone/davfs-папкой.
Border не монтирует ресурсы и не хранит их учётные данные в панели. Пока папка
не настроена, оставьте `FileExport` отсутствующим: скачивание работает независимо.

1. Подключите сетевой ресурс средствами ОС. Например, точка монтирования
   `/mnt/backups`, отдельный существующий каталог `/mnt/backups/border`.
   Дайте службе право создавать, читать и переименовывать файлы/каталоги.
   Для NFS с root-squash настройте подходящие права на стороне хранилища.
2. Добавьте в привилегированную конфигурацию:

   ```json
   "FileExport": {
     "ID": "offsite-main",
     "MountPoint": "/mnt/backups",
     "Directory": "/mnt/backups/border"
   }
   ```

3. Добавьте drop-in `border-backup.service`:

   ```ini
   [Service]
   ReadWritePaths=/mnt/backups/border
   ```

   Каталог точки монтирования должен существовать и при отключённой сети, иначе
   systemd не запустит worker и не обновит очередь. Сам worker запрещает запись
   на локальную файловую систему при отсутствии сетевого монтирования. Для папки
   в `/home` нужно отдельно адаптировать `ProtectHome`. Учитывайте сетевые таймауты
   монтирования: зависшая операция файловой системы ограничивается настройками ОС
   и таймаутом службы, а не только HTTP/Go-контекстом.
4. Выполните `systemctl daemon-reload`, затем
   `radiusd backup init-file-export --config /etc/border-backup.json`.
   Команда создаёт маркер назначения и отказывается его перезаписывать.
   Включите таймер; после его запуска назначение появится в панели.
5. В разделе **Выгрузка файлами** включите автоматическое копирование. Смена ID
   или пути отключает его; старые задания не перенаправляются в новую папку.

В очередь попадут уже имеющиеся проверенные архивы и все новые. На один архив
и назначение создаётся одно задание; выполняется одна передача за запуск таймера.
Архив проверяется до копирования, записывается во временный каталог, читается
обратно для SHA-256 и публикуется переименованием каталога. Итоговая структура:

```text
backup-<ID>/
  backup-<ID>.tar.gz.age
  backup-<ID>.tar.gz.age.sha256
```

При повторе готовый комплект проверяется и не переписывается. Несовпадающий файл
в назначении вызывает ошибку, чужие данные не заменяются. Ключ расшифровки
не выгружается. Ошибки временной недоступности/передачи повторяются с задержками
1, 5, 15, 60 и 180 минут (всего до шести попыток). После перезапуска worker
продолжает очередь с сохранённым числом попыток; сбой после записи файла до
фиксации результата в БД не создаёт дубль. Ошибки исходного архива и конфликт
назначения требуют вмешательства. Кнопки повторной подготовки и отмены доступны
в панели. Отмена выполняющейся передачи может оставить уже записанный файл.

Ротация сетевых копий этой версией не выполняется: срок их хранения задавайте на
стороне хранилища. Отчёт SHA-256 подтверждает совпадение прочитанных байтов;
долговечность записи при отказе хранилища зависит от его настроек. После подключения
реальной папки проверьте передачу, отключение сети и восстановление скачанного
комплекта на отдельном хосте.

## Восстановление

Храните ключ и проверенные архивы также **вне сервера**. Локальный таймер сам по
себе не обеспечивает удалённое хранение. Для восстановления нужны архив и отдельный
ключ age; `BORDER_MASTER_KEY` уже находится внутри зашифрованной копии.

```sh
radiusd backup restore /path/backup-ID.tar.gz.age \
  --key /secure/identity.txt --to /root/border-recovery
```

Команда создаёт **новый** каталог и отказывается перезаписывать существующий.
При ошибке проверки удаляет только созданный ею каталог. Все извлечённые файлы
остаются закрытыми (0600), каталоги — 0700. В `manifest.json` записаны исходные пути,
режимы, размеры и контрольные суммы. Базы лежат в `databases/root.db` и
`databases/tenants/ID.db`, конфигурация и бинарник — в `files/` с исходной структурой.

Для переключения на восстановленную систему администратор отдельно:

1. Останавливает `border-backup.timer` и `border-backup.service`, затем `border.service`.
2. Сохраняет текущие данные и окружение для обратного переключения.
3. Восстанавливает **одним комплектом** базы всех тенантов, окружение, сертификаты
   и бинарник. Не оставляет старые `-wal`/`-shm` рядом с восстановленными базами.
4. Возвращает права: данные принадлежат `border`, бинарник root:root 0755,
   окружение root:root 0600; серверный сертификат/ключ доступны службе Border.
   Применяет подходящие для нового хоста unit и пути. Сам ключ age берётся отдельно.
5. Проверяет конфигурацию внешних служб и запускает Border сначала в изолированной
   сети: вход в панели тенантов, чтение CA, LDAP и тестовая авторизация RADIUS.
6. Возвращает рабочие подключения и расписание после проверки. Проверяет очередь
   публикаций/уведомлений: состояние сохранено на момент снимка, доставки уже могли
   произойти после него.

Автоматической перезаписи работающего сервера из панели нет.
