# Тенанты, домены, расположения и политики

Border 0.4 сохраняет прежнюю конфигурацию основного экземпляра. Новые политики
действуют после явной привязки к NAS; NAS без привязки использует прежние правила.

## Тенанты

Основной администратор создаёт тенанта в меню «Тенанты» с отдельным начальным
администратором. Панель: `/t/<id>/`, личный кабинет: `/portal/<id>/`.
Личный кабинет основного экземпляра: `/portal/default/`.

У тенанта собственные пользователи, LDAP, политики, сертификаты и ключи CA,
устройства, наблюдения fingerprint, настройки и кэш Fingerbank, подписки push.
SQLite использует отдельные файлы в `--tenant-dir` (по умолчанию `tenants` в рабочем
каталоге); PostgreSQL — отдельные схемы и отдельные пулы соединений. Пароли
сервисов шифруются производным ключом каждого тенанта. Администратор платформы
не получает автоматическую веб-сессию в панели тенанта. Владельцы сервера и
PostgreSQL остаются доверенными администраторами инфраструктуры.

NAS выбирается по IP источника UDP. Один IP не может обслуживать несколько
тенантов на общем слушателе: неоднозначные запросы отклоняются. Для NAS за одним
NAT понадобятся разные адреса источника или отдельные экземпляры Border.

При создании копируется открытый справочник IEEE OUI основного экземпляра.
Наблюдения устройств и ключ Fingerbank не копируются. Для резервной копии
остановите службу и сохраните всю базу платформы, каталог всех тенантов и master
key. Команда переноса SQLite→PostgreSQL отказывается переносить непустой каталог
тенантов как одну БД: требуется перенос каждой базы и восстановление каталога.

## Порядок настройки

1. В «Настройки» создайте домены с собственными LDAPS/StartTLS-подключениями.
   До трёх серверов одного домена могут использовать общий Base DN, bind DN,
   пароль службы, атрибут логина и доверенный CA. Между доменами переключения нет.
   Изменение адреса сервера требует повторного ввода пароля службы.
2. В «Пользователи» создайте локальных пользователей либо используйте доменных.
   Имена имеют вид `local/ivan` или `corp/ivan`; одинаковые короткие логины не
   объединяются. Локальные пользователи не являются администраторами панели.
3. В «Политики авторизации» выберите источник проверки: локальный пароль,
   пароль конкретного LDAP-домена, одноразовый код, MAC или EAP-TLS. Для пароля
   можно потребовать TOTP. Пользователь настраивает TOTP в личном кабинете.
4. В «Расположения и сегменты» создайте расположения и логические сегменты,
   например `office-msk` и `employees`. Привяжите сегмент к VLAN расположения.
   При необходимости задайте VLAN этого же сегмента для конкретного NAS.
5. В «Политики доступа» выберите политику авторизации, назначение сеть/SSH/VPN,
   список разрешённых личностей, даты начала/окончания, максимальную длительность
   сессии и таймаут простоя. Для сети укажите логический сегмент; для SSH/VPN —
   поддерживаемые словарём атрибуты прав. Списки пока явные, без LDAP-групп.
6. В «Сетевые устройства» выберите словарь, назначение, расположение и политику
   доступа. Назначение политики и NAS должно совпадать.

Для пароль+TOTP используется PAP: поле пароля `пароль;otp=123456`.
Это сочетание проверяется как AND; резервный или почтовый код не заменяет TOTP.
Обычный пароль и MAC не дают обхода второго фактора. PAP ограничивает длину
полного поля пароля 128 байт. Применяйте защищённую транспортную сеть между NAS и
Border. PEAP/MSCHAPv2, EAP chaining и произвольные цепочки факторов пока не
поддерживаются. strongSwan EAP-MSCHAPv2 и SSH/VPN Keenetic остаются отключёнными.

Нет соответствия сегмент→VLAN — нет доступа. NAS-переопределение имеет приоритет
над расположением. Срок `Session-Timeout` не превышает остаток срока политики.
Завершение уже открытой сессии зависит от исполнения этого атрибута устройством;
изменение политики само по себе не отправляет Disconnect всем текущим сессиям.
Даты UI вводятся в часовом поясе браузера и сохраняются как Unix timestamp.

## Уведомления

Меню «Настройки» → «Каналы уведомлений»: область «Тенант» задаёт значения по
умолчанию для локальных пользователей и доменов. Для каждого домена SMTP, SMS и
Push независимо имеют режим «наследовать», «собственные настройки» или «выключен».
Ошибки провайдера не вызывают перехода на чужие реквизиты. Область определяется
доменом учётной записи, не суффиксом email. При первом обновлении прежние SMTP
переменные окружения и SMS-настройки импортируются как настройки основного
тенанта; затем настройки панели имеют приоритет.

SMTP использует проверяемый TLS: implicit TLS либо обязательный STARTTLS.
SMS поддерживает HTTPS webhook (`{ "to": "+79991234567", "text": "..." }`,
Bearer token) и Twilio. Телефон локального пользователя задаёт администратор,
доменного — атрибут `mobile` LDAP. События безопасности отправляются во включённые
каналы, если есть адрес/телефон/подписка. Почтовый одноразовый код направляется
только через SMTP. Гостевые SMS используют канал домена политики NAS, либо канал
тенанта для устройств без доменной политики. Новая политика доступа имеет
приоритет над прежними гостевыми разрешениями.

Для push укажите контактный email VAPID. Ключи создаются и хранятся автоматически.
Пользователь сам нажимает «Подключить уведомления» в личном кабинете и разрешает
уведомления браузеру. До 10 подписок на пользователя, подписки зашифрованы и
привязаны к аккаунту и ключу области. Перед сменой аккаунта в одном браузере
нужно отключить подписку. Поддержаны push endpoints Google, Mozilla, Apple и
Windows; сторонние endpoints, HTTP, перенаправления и частные IP отклоняются.
Push содержит общее сообщение о событии безопасности, без паролей и кодов.

Требуется HTTPS и поддержка Push API браузером; на iOS может потребоваться
установка веб-приложения на домашний экран. Кнопка проверки отправляет реальное
push-сообщение, её использование ограничено. Реальная доставка SMTP/SMS/Push
требует настройки провайдера и проверки на целевом устройстве. Очередь с
повторными попытками доставки пока не реализована.
