# Роли и изоляция панели

Раздел «Конфигурация → Доступ к панели → Администраторы и роли» управляет
учётными записями в текущей базе. Существующие администраторы после миграции 23
сохраняют права. Новые записи по умолчанию предлагается создавать наблюдателями.

- Администратор платформы — администратор корневой панели: управляет каталогом
  тенантов и корневой конфигурацией. Это контекст root, а не переносимое право
  из базы тенанта. В чужие панели он входит отдельной учётной записью тенанта.
- Администратор тенанта (`admin`) — полный доступ в своей базе, включая роли.
- Оператор (`operator`) — одна обязательная локация; видит её сессии, может
  отправить Disconnect и повторить уже запланированный отзыв. CoA со сменой VLAN,
  настройки NAS, политики, сертификаты, общие журналы и экспорты ему недоступны.
- Наблюдатель (`viewer`) — сессии и журнал своего тенанта без изменений.
  Конфигурации, ключи, экспорт базы и список администраторов ему недоступны.

Оператор и наблюдатель получают отдельную страницу с поиском и пагинацией.
Ограничения действуют в серверном middleware по явному списку разрешённых
маршрутов; неизвестные им API закрыты, даже если вызвать их напрямую.
Фильтр оператора добавляется к SQL до подсчёта строк и пагинации. Локация берётся
из учётной записи, не из параметров запроса. Перед действием повторно проверяется
принадлежность NAS локации, затем действует существующая проверка поколения сессии.
Назначение нескольких локаций одной учётной записи пока не поддерживается.

Сессия входа содержит имя и ревизию учётной записи. На каждом запросе проверяются
действующий статус и ревизия. Сохранение записи (включая пароль/роль/локацию)
аннулирует прежние cookie; Basic Auth также учитывает актуальные права.
CLI-сброс пароля увеличивает ревизию. Нельзя отключить или понизить последнего
активного администратора. Проверка выполняется в транзакции с блокировкой записи
(SQLite) либо таблицы учётных записей (PostgreSQL).

GET `/api/me` возвращает текущую личность и область. GET/POST `/api/admins`
доступны только администраторам. POST принимает Username, Password (пустой
сохраняет прежний), Role, LocationID, Enabled. Хеши паролей не возвращаются.
Изменения и ручные действия над сессиями записываются с именем оператора.

Ролевые аккаунты остаются в отдельных базах тенантов. Cookie и пароли одного
тенанта не дают доступа к другому (если там отдельно не создана учётная запись
с тем же паролем). Корневой каталог тенантов не появляется в дочерних панелях.
Фоновые AAA/отзыв/LDAP-задачи продолжают работать в своём Runtime/Store и не
наследуют права вошедшего оператора.

Проверены прямые запреты API, подмена локации в запросе, фильтрация сессий,
аннулирование cookie после смены локации, блокировка Basic Auth, запрет потери
последнего администратора и границы между двумя тенантами. Это первый этап RBAC,
а не утверждение о завершённом независимом аудите безопасности всего продукта.

MFA, резервные коды и отдельные токены мониторинга описаны в [защите входа](ADMIN-MFA.md).
Basic Auth запрещён для учётных записей с активной MFA.
