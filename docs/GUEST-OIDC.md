# OIDC для гостевого портала

Border поддерживает стандартный OIDC Authorization Code с PKCE S256. Вход
проверяет Go-сервер; клиентский браузер не получает ID Token, access token или
Client Secret. Реальный провайдер пока не зарегистрирован: проверка выполнена
на локальном TLS-стенде с discovery, JWKS, token endpoint и подписанными JWT.
Физический captive NAS проверяется отдельно.

## Настройка

1. В политике авторизации выберите **OIDC · гостевой портал**, цепочку
   **Основная проверка**. Опубликуйте черновик.
2. Создайте сетевую политику доступа с этой авторизацией, логическим сегментом,
   сроками и длительностью сессии. Опубликуйте разрешающие правила: например,
   «Все прошедшие авторизацию» с ограничением по расположению/NAS. Без
   разрешающего правила или явной личности вход не даёт доступа.
3. Привяжите политику к NAS, напрямую или через набор политик с протоколом
   **MAB**. Первая подходящая привязка должна выбирать эту OIDC-политику.
   Сопоставьте сегмент с VLAN NAS или расположения. Включите captive portal
   на NAS и общий гостевой режим в настройках гостевого доступа.
4. Откройте **Конфигурация → Интеграции → Гостевой вход · OIDC**. Выберите
   тенант, домен или NAS, слот кнопки и опубликованную политику доступа.
   Заполните Issuer URL, Client ID и способ аутентификации клиента:
   `client_secret_basic`, `client_secret_post` либо публичный клиент без секрета.
5. Скопируйте **Callback URL** в регистрацию приложения у провайдера без
   изменения пути. Для основной базы это
   `https://border.kislovs.ru/portal/default/api/guest/oidc/callback`, для тенанта —
   `https://border.kislovs.ru/portal/<tenant>/api/guest/oidc/callback`.
6. Введите Client Secret, если он требуется, включите подключение и сохраните.
   В конструкторе captive portal включите SSO и соответствующую кнопку.

Провайдер должен иметь HTTPS discovery/JWKS/token endpoint, поддерживать PKCE
S256, `response_mode=query` и подпись ID Token RS256 либо ES256. Запрашиваются
scopes `openid email profile`. Произвольные OAuth2, Яндекс OAuth, ЕСИА и
особые механизмы Apple не становятся OIDC от выбора названия кнопки: для
несовместимых протоколов нужен отдельный адаптер или OIDC-брокер.

Для частного Keycloak включите опцию частной сети. Она разрешает сетевые
адреса, но сохраняет проверку TLS: сертификату должен доверять сервер Border.
По умолчанию запросы к частным, локальным и служебным адресам запрещены;
HTTP и переходы discovery/token/JWKS на другой URL запрещены. Не отключайте
проверку сертификатов. При запросах используются ограничение размера и таймауты.

## Области и доступ

У каждой кнопки собственное наследование подключения: NAS → домен из
подписанного NAS-перехода → тенант. Выключенная запись блокирует наследование
этой кнопки. Оформление наследуется целиком по прежним правилам. Тенанты
используют отдельные базы и ключи шифрования.

Необязательный список доменов email требует точного совпадения домена и
`email_verified=true` в ID Token. Пустой список допускает любую личность
провайдера, разрешённую политикой. Email не связывается с локальным/LDAP-логином.
Постоянная личность — `oidc:` плюс SHA-256 от `issuer + NUL + sub`; её можно
взять из журнала/списка гостей, включить в список политики или локальную группу.
Блокировка этой личности через существующий `identity_status` отзывает доступ.
Состояние аккаунта у IdP непрерывно не опрашивается; logout/back-channel logout
и синхронизация блокировок IdP пока не реализованы.

OIDC не выполняет и не обходит цепочки пароля/TOTP, SSH, VPN или EAP. Такой
источник разрешён только для сетевой политики и проверки `primary` в портале.
Уже администрируемые MAC (в том числе выключенные) не получают гостевой доступ.
До подтверждения OIDC запрос RADIUS по этой политике отклоняется; NAS должен
сам обеспечивать доступ к странице входа и к нужным доменам IdP до авторизации.

После callback необходимо переподключение к Wi-Fi/повторная MAC-аутентификация
на NAS. Border не отправляет VLAN-only CoA старой сессии: новый Access-Accept
содержит Class, связывающий Accounting с OIDC-личностью и политикой. NAS должен
возвращать Class в accounting. User-Name — MAC, Calling-Station-Id при наличии
должен совпадать. Обычная диагностика сессий показывает отсутствие этой связи.
Правила и привязки, требующие SSID/Service-Type/NAS-Port-Type, не совпадут при
входе через текущий подписанный редирект без этих селекторов: ограничения
не игнорируются. Используйте отдельный NAS/политику с доступными селекторами.

VLAN берётся из сопоставления сегмента для NAS/расположения. Срок доступа —
минимум длительности сессии политики, её `ValidUntil` и срока ID Token; общий
SMS-VLAN/TTL его не заменяет. Проверки выполняются перед входом, после обмена
кода, перед выдачей RADIUS-доступа и в рабочем процессе отзыва сессий.
Изменение провайдера отзывает прежние разрешения в затронутой области.
Изменение политики/привязки/VLAN, отключение домена, истечение срока и ручной
отзыв также запрещают новые входы и ставят учтённые сессии на обычный отзыв NAS.
Фактическое отключение зависит от ответа NAS; результат виден в диагностике.

## Защита и эксплуатация

- State, nonce и PKCE создаются случайно. State связан с HttpOnly/Secure/
  SameSite=Lax cookie браузера и проверенным NAS/MAC/доменом, действует 5 минут
  и используется один раз. Перезапуск отменяет незавершённые входы; сохранённые
  разрешения восстанавливаются из базы и повторно проверяются.
- Проверяются подпись, issuer, audience/azp, nonce, время выдачи и истечения;
  при наличии проверяется `at_hash`. Нет доверия к email или токену из браузера.
- Callback всегда возвращает на локальную страницу результата через 303.
  Код и state не переносятся в URL результата. На внешнем прокси исключите
  query callback из access logs. Токены/секреты не пишутся в аудит.
- Лимиты: 10 попыток начала на IP за 15 минут, один старт на NAS/MAC в минуту,
  до 1000 одновременных потоков на тенант. Недоступность IdP не даёт доступа.
- Секрет хранится зашифрованным, API возвращает только `HasSecret`. При смене
  Issuer/Client ID/AuthStyle прежний секрет не переносится. Сохранение защищено
  от потери чужих изменений через Revision. Секреты входят в проверку
  восстановления зашифрованной резервной копии (схема 36).

API администратора: GET `/api/guest/oidc?scope=tenant|domain:ID|nas:IP`, POST
`/api/guest/oidc` с OIDCConfiguration. Доступ только администратору, изменение
требует CSRF. Общий `/api/guest/config` включает OIDC-гостей в Sessions;
`/api/guest/revoke` отзывает разрешение по NAS/MAC.

Публичный POST `/api/guest/design` возвращает `OIDC:[{ID,Name}]` без настроек и
секретов. POST `/api/guest/oidc/start` принимает `{Token,Provider}`; callback
GET `/api/guest/oidc/callback` проверяет поток и выдаёт короткоживущий результат.

Проверки: `go test ./...`, `go vet ./...`, race-тесты затронутых пакетов.
OIDC TLS-стенд проверяет успешный обмен, подпись/claims, повторы, чужой браузер,
изменение конфигурации и политики, запрет зарегистрированных MAC, блокировку
личности, наследование и закрытый сетевой доступ. RADIUS-тест проверяет VLAN,
Session-Timeout, Class/Accounting и постановку на отзыв.

Основа протокола: [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html),
реализация проверки токенов: [coreos/go-oidc](https://github.com/coreos/go-oidc).
