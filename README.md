# Border

RADIUS-сервер на Go с встроенной веб-панелью управления.

**Автор: Кислов Роман Сергеевич. Лицензия: Apache License 2.0.**

Border собирается в **один исполняемый файл `radiusd`**. Он содержит UDP RADIUS-сервер, HTTPS-панель, статические ресурсы, SQL-миграции и CLI. Для запуска не нужны FreeRADIUS, Node.js, nginx или Go. SQLite работает без CGO. Файл базы данных и сертификаты хранятся отдельно; PostgreSQL при его выборе является внешним сервисом.

## Статус

Текущая версия, **0.3.0-dev**: RADIUS MAB, EAP-TLS и одноразовые коды по PAP, административная панель и отдельный портал самообслуживания с доменным входом, TOTP и управляемой PKI. Добавлена поддержка EAP-TLS (TLS 1.2) с управляемыми клиентскими сертификатами; независимый eapol_test проверяет полный обмен и MPPE-ключи. Добавлены SMS-портал, база fingerprint, профили NAS и отдельная PAP-авторизация SSH/VPN. PEAP/MSCHAPv2 пока не поддерживаются. [План разработки](docs/ROADMAP.md) описывает оставшуюся работу.

Реализовано:

- RADIUS Authentication UDP 1812 и Accounting UDP 1813 на Go, библиотека `layeh.com/radius` для кодирования и разбора пакетов.
- Фиксированный пул обработчиков, ограниченная очередь, отбрасывание пакетов при перегрузке.
- Доверенные NAS по точному IP, индивидуальные общие секреты. Обязательный Message-Authenticator для **всех** Access-Request, включая MAB; проверка HMAC и подпись ответов.
- MAB по Calling-Station-Id с резервным User-Name. Нормализация четырёх форматов MAC, запрет отключённых устройств.
- Data VLAN, явный voice VLAN с Cisco AVPair, изоляционный VLAN для неизвестного MAC и default VLAN на NAS.
- Accounting Start / Interim-Update / Stop, журнал решений, сохранение Proxy-State.
- EAP-TLS (TLS 1.2), Access-Challenge/State, фрагментация в обе стороны, повторная передача, проверка отзыва, экспорт MSK и зашифрованные MS-MPPE ключи.
- Dynamic Authorization: CoA для изменения VLAN и Disconnect для завершения записанных активных сессий, проверка ACK/NAK и Error-Cause.
- Веб-панель: создание, обновление и удаление NAS, MAC, VLAN; политика изоляции; просмотр сессий и аудита. Повторный IP/MAC/ID обновляет запись.
- HTTPS и обычная форма входа администратора по логину/паролю; опциональный обязательный mTLS через `--admin-mtls`. Bcrypt, защищённые cookie, CSRF, CSP, лимиты запросов.
- Отдельный пользовательский HTTPS-портал: доменный вход через AD или FreeIPA (LDAPS/StartTLS), TOTP с QR-кодом, 10 резервных кодов, почтовые коды доступа.
- SMTP через обязательный STARTTLS или implicit TLS, доменный адрес доставки и уведомления о действиях с кодами/сертификатами.
- Управление CA: создание и импорт, выпуск клиентских сертификатов, перевыпуск с новым ключом и отзывом старого, отзыв, подписанные CRL. Личные операции ограничены владельцем.
- ACME-клиент: настройка через панель, получение и автоматическое продление HTTPS-сертификата, зашифрованный кэш ключей и ACME-аккаунта.
- SQLite и PostgreSQL с одной встроенной схемой Goose; транзакционный перенос данных в пустую PostgreSQL БД.
- CLI для инициализации, создания/восстановления администратора и генерации сертификатов.

MAB доверяет MAC, переданному зарегистрированным NAS, и сам по себе не подтверждает личность пользователя. NAS должен добавлять Message-Authenticator; запросы старых устройств без него отбрасываются.

Готовые архивы предварительных выпусков доступны в разделе [Releases](https://github.com/rkislov/border/releases). В каждом архиве один исполняемый файл и сопроводительные лицензии/документация.

## Сборка

Требуется Go **1.26.10+** (версии закреплённых зависимостей указаны в `go.mod`).

```sh
make build
./bin/radiusd --version
```

Для другой системы соберите отдельный бинарник, например Linux amd64:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags='-s -w' -o bin/radiusd-linux-amd64 ./cmd/radiusd
```

Бинарник самодостаточен для своей ОС и архитектуры. Ресурсы читаются из `embed.FS`, текущая папка с исходниками для запуска не нужна.

## Быстрый старт: SQLite

```sh
./bin/radiusd init-db
./bin/radiusd create-admin admin
./bin/radiusd gen-certs --host localhost
./bin/radiusd serve
```

Пароль вводится дважды в терминале без отображения; минимальная длина — 12 байт. Передавать пароль аргументом CLI нельзя.

По умолчанию:

- веб: `https://localhost:8443`, слушает только `127.0.0.1`;
- authentication: UDP `:1812`;
- accounting: UDP `:1813`;
- база: `border.db`;
- сертификаты: `certs/`;
- 256 обработчиков на каждый UDP-порт.

Для браузера установите доверие к `certs/ca.pem` и откройте `https://localhost:8443`. По умолчанию достаточно логина и пароля администратора. Чтобы дополнительно требовать клиентский сертификат, запускайте `serve --admin-mtls`. Для этого режима импортируйте административный сертификат в браузер. Если браузеру нужен PKCS#12, создайте его локально:

```sh
openssl pkcs12 -export -out certs/admin.p12 -inkey certs/admin.key -in certs/admin.pem -certfile certs/ca.pem
```

OpenSSL нужен только для этого преобразования; сервер от него не зависит. При включённом `--admin-mtls` выберите сертификат `Border admin`, затем введите имя/пароль в форме. Без флага сертификат не требуется. Для проверки через curl:

```sh
curl --cacert certs/ca.pem --cert certs/admin.pem --key certs/admin.key --user admin https://localhost:8443/api/state
```

В панели создайте VLAN, затем NAS и разрешённые MAC. Для NAS укажите точный IP-адрес источника запросов (при NAT — адрес после NAT) и случайный общий секрет не короче 16 байт. Параметры NAS должны совпадать с сервером.

Чтобы изменить запись, заполните форму с тем же IP, MAC или VLAN ID. Для блокировки MAC снимите «Активно» и сохраните запись. Если VLAN не выбран, NAS использует свой сегмент по умолчанию. Voice-режим назначается явно; автоматического OUI-распознавания пока нет.

Изоляция неизвестных MAC выключена по умолчанию: Access-Reject. В разделе «Политики» можно выбрать изоляционный VLAN. Запрет для отключённой записи имеет приоритет над изоляцией.

## PostgreSQL

Используйте отдельную БД и учётную запись. Передавайте DSN через окружение, чтобы не записывать пароль в историю команд с аргументами.

```sh
export BORDER_DB_DRIVER=pgx
# Задайте BORDER_DB через защищённую конфигурацию окружения:
# postgres://border:...@db.example.net:5432/border?sslmode=verify-full
./bin/radiusd init-db
./bin/radiusd create-admin admin
./bin/radiusd serve --web 0.0.0.0:8443 --certs /etc/border/certs
```

Пути и параметры также доступны через `--db-driver`, `--db`, `--web`, `--auth`, `--accounting`, `--workers`, `--certs`. `init-db` выполняет идемпотентные миграции; `serve` требует уже созданную схему.

Для production используйте сертификаты вашей PKI, ограничьте сетевой доступ к UDP-портам доверенными NAS и храните файл SQLite/резервные копии с правами владельца процесса. Общие секреты NAS сохраняются в БД, поскольку нужны RADIUS-протоколу; они не возвращаются в API и не выводятся в лог. CA-ключ `ca.key` после выдачи сертификатов храните отдельно от сервера. Обновление bootstrap-файлов серверного сертификата требует перезапуска. Управляемая PKI публикует CRL; OCSP пока не реализован. Управляемые пользовательские CA не добавляются автоматически в доверенные CA административного mTLS.

## SQLite → PostgreSQL

Остановите сервер и сделайте резервную копию SQLite. Целевая PostgreSQL БД должна быть новой и пустой. `migrate-db` создаёт схему назначения и копирует данные одной транзакцией. Непустые прикладные таблицы назначения приводят к отказу; существующие записи не перезаписываются.

```sh
export BORDER_SOURCE_DB=/var/lib/border/border.db
# Задайте BORDER_TARGET_DB через защищённое окружение.
./bin/radiusd migrate-db
```

Первичные ключи — UUID, MAC, IP и явные VLAN ID; sequence для прикладных таблиц не используются. Служебная таблица Goose создаётся заново миграциями. После переноса переключите `BORDER_DB_DRIVER=pgx` и `BORDER_DB`, проверьте панель и запустите сервер. Копирование между уже работающими инсталляциями не поддерживается.

## Обновление с 0.1.0

Остановите `radiusd`, сохраните БД, сертификаты и `BORDER_MASTER_KEY`, замените бинарник и выполните `radiusd init-db` с прежней конфигурацией БД. Эта версия добавляет настройки EAP и CoA-порт NAS. EAP по умолчанию выключен. Перенос SQLite → PostgreSQL также обновляет схему исходной БД перед копированием; выполняйте его на остановленном сервере после резервного копирования.

## Wi-Fi Enterprise: EAP-TLS

1. Задайте постоянный `BORDER_MASTER_KEY`, выполните `init-db` и запустите сервер.
2. Создайте управляемый CA в панели, выпустите клиентский сертификат через панель или доменный личный кабинет.
3. В «Политиках» включите EAP-TLS и выберите VLAN. Настройки применяются без перезапуска; отключение запрещает и новые входы, и завершение незаконченных обменов.
4. На точке доступа задайте RADIUS UDP 1812, IP сервера и секрет зарегистрированного NAS. Используйте WPA2/WPA3-Enterprise с EAP-TLS.
5. На клиенте установите личный сертификат и ключ, доверие к **CA серверного сертификата** и проверку DNS-имени сервера. TLS-сертификат RADIUS берётся из `certs/server.pem` и `server.key`; выдайте его для реального DNS-имени с `gen-certs --host` либо установите сертификат вашей PKI.

CA клиентских сертификатов и CA серверного сертификата могут различаться. PEM, скачанный пользователем, содержит личный ключ, клиентский сертификат и его CA; доверие к серверному CA настраивается отдельно администратором. Не отключайте проверку сервера на клиентах.

Аутентифицированная идентичность берётся из CN сертификата, а не из внешней EAP Identity. Сервер требует точную активную запись этого сертификата в управляемой PKI: неизвестный, отозванный или истёкший сертификат получает отказ. Отзыв учитывается без перезапуска для новых аутентификаций. Уже работающий сеанс NAS завершается через Disconnect или очередную реаутентификацию; автоматического отключения при отзыве пока нет. Сертификаты произвольной внешней PKI вне реестра Border пока не принимаются.

Реализован RFC 5216 с TLS 1.2; TLS 1.0/1.1 и TLS 1.3 EAP (RFC 9190) не включаются. Возобновление TLS-сессий отключено, чтобы каждый новый вход проходил полную проверку сертификата. EAP-контекст привязан к NAS, Calling-Station-Id и порту, живёт до 30 секунд; одновременно допускается до 256 контекстов. TLS-flight ограничен 64 KiB, исходный фрагмент — 1000 байт. Повторный ответ клиента получает прежний EAP-ответ; ключи выдаются только после завершающего ACK.

Пример для supplicant и независимой проверки — [examples/eap-tls.conf](examples/eap-tls.conf). `eapol_test` нужен только для тестов, сервер от него не зависит:

```sh
BORDER_EAPOL_TEST=/path/to/eapol_test go test -race -run TestEAPOLInteroperability -v ./internal/aaa
```

Тест использует реальные UDP-пакеты, фрагментацию в обоих направлениях, повторную аутентификацию и проверку MPPE-ключей. Проверки с конкретными физическими AP/коммутаторами остаются отдельным этапом.

## CoA и Disconnect

В карточке NAS задайте UDP-порт динамической авторизации (по умолчанию 3799), разрешите запросы от IP Border на NAS и используйте тот же общий секрет. В разделе «Сессии» выберите активную запись: можно отправить Disconnect или CoA с целевым VLAN из справочника.

Адрес назначения и идентификатор берутся только из зарегистрированного NAS и записанной accounting-сессии; произвольный адрес отправки через API не принимается. Запросы содержат Event-Timestamp и Message-Authenticator. Проверяются подпись ответа, Identifier, тип ACK/NAK, а также Message-Authenticator и Event-Timestamp при их наличии в ответе. Таймаут — 4 секунды, повтор — через секунду. Ответ NAS и Error-Cause попадают в аудит.

Disconnect-ACK отмечается локально как `disconnect-ack`, после чего ожидается Accounting Stop. CoA-ACK подтверждает изменение на NAS, но не меняет постоянную MAB/EAP-политику: при следующем входе она применяется заново. Не все NAS допускают динамическую смену VLAN; при NAK панель показывает причину. Автоматического обхода отказа через Disconnect нет.

## Портал самообслуживания, почта и PKI

Всё работает в том же `radiusd`, на отдельных слушателях. Административная панель — `127.0.0.1:8443`, личный кабинет — `127.0.0.1:9443`, обработчик ACME HTTP-01 — `127.0.0.1:8080`. Адреса меняются флагами `--web`, `--portal`, `--acme-http`.

Для этих модулей задайте **постоянный** мастер-ключ. Он шифрует TOTP, закрытые ключи CA и ACME-кэш и участвует в HMAC кодов. Сохраните его в защищённом окружении процесса, отдельно от БД; потеря ключа делает зашифрованные данные недоступными. Смена ключа без миграции не поддерживается.

```sh
./bin/radiusd gen-key
# Сохраните выведенное значение как BORDER_MASTER_KEY в защищённой конфигурации.
./bin/radiusd init-db
./bin/radiusd serve --portal-url https://portal.example.net
```

Без `BORDER_MASTER_KEY` базовый MAB и административный вход работают, а пользовательский портал, управляемая PKI и ACME отключены. Настройки подключений берутся из окружения; программа не загружает `.env` автоматически. Полный пример — [.env.example](.env.example).

### AD и FreeIPA

Настройте `BORDER_LDAP_URL`, `BORDER_LDAP_BASE_DN`, `BORDER_LDAP_BIND_DN`, `BORDER_LDAP_BIND_PASSWORD`. Анонимный поиск запрещён. Используйте техническую учётную запись только с правом чтения.

- AD: `BORDER_LDAP_USER_ATTRIBUTE=sAMAccountName` (короткий логин) или `userPrincipalName` (полный UPN).
- FreeIPA: `BORDER_LDAP_USER_ATTRIBUTE=uid`.
- `ldaps://host:636` использует TLS сразу; `ldap://host:389` всегда выполняет StartTLS до bind.
- `BORDER_LDAP_CA` — путь к PEM дополнительного доверенного CA. Проверка TLS не отключается.

При входе сервер ищет одну запись по выбранному атрибуту, выполняет пользовательский bind и берёт почту из `mail`. Без доменной почты вход не разрешён. Доменный пароль не сохраняется. Режим выбирается конфигурацией одной директории на инсталляцию; одновременная федерация нескольких доменов пока не поддерживается.

Личная сессия живёт 10 минут. Успешный доменный вход сбрасывает блокировку попыток ввода сетевых кодов. Для кодов уже зарегистрированной учётной записи дополнительный LDAP-поиск при каждом RADIUS-запросе не выполняется; отзыв учётной записи в каталоге пока не отзывает ранее выданные TOTP и сертификаты автоматически.

### Коды и SMTP

Настройте `BORDER_SMTP_ADDRESS=mail.example.net:587`, `BORDER_SMTP_FROM`, при необходимости `BORDER_SMTP_USERNAME`/`BORDER_SMTP_PASSWORD`. По умолчанию обязателен STARTTLS; для порта 465 укажите `BORDER_SMTP_TLS=implicit`. Дополнительный CA — `BORDER_SMTP_CA` (PEM-файл).

Личный кабинет позволяет:

- отправить на доменный адрес 8-значный сетевой код на 5 минут; повторная отправка не раньше 60 секунд, новый код аннулирует старый;
- подключить или перевыпустить TOTP с QR-кодом и подтверждением первого кода (30 секунд, допуск ±1 шаг, защита от повтора);
- перевыпустить 10 одноразовых резервных кодов, действующих до года; старый набор сразу аннулируется;
- получить уведомление о смене TOTP, резервных кодов и операциях с сертификатами. Сбой уведомления отображается отдельно от уже выполненной операции.

Коды и TOTP можно использовать через RADIUS **PAP**: User-Name — канонический доменный логин, User-Password — код. Все Access-Request должны иметь Message-Authenticator. Неверный код не приводит к MAB даже при известном Calling-Station-Id. `BORDER_PORTAL_VLAN` задаёт общий VLAN для этого режима (0 — default NAS); VLAN должен быть в справочнике. После 5 неверных попыток коды блокируются до нового доменного входа. Почтовые и резервные коды потребляются атомарно и повторно не принимаются.

SMS-портал с подписанным редиректом описан в [руководстве](docs/GUEST-FINGERPRINTS.md). Готовые адаптеры оборудования, PEAP и второй фактор администратора остаются в плане.

### CA, выпуск и отзыв

Раздел «Сертификаты и CA» административной панели позволяет создать ECDSA CA или импортировать существующий CA с соответствующим ключом PKCS8 PEM. CA должен допускать подпись сертификатов и CRL. Закрытый ключ зашифрован в БД и не возвращается API. CA из этой панели предназначены для пользовательских клиентских сертификатов и отделены от bootstrap-CA административного mTLS.

Администратор выдаёт сертификаты сроком 1–365 дней, пользователи в личном кабинете — личные сертификаты на 90 дней с CN доменного логина и SAN доменной почты. Сертификаты имеют EKU ClientAuth; это не сертификаты веб-серверов. Срок не может превышать срок CA. Ключ генерируется на сервере, передаётся по HTTPS один раз в PEM-скачивании и не сохраняется в БД. Храните скачанный PEM как секрет.

При перевыпуске создаётся новая ключевая пара, а старый сертификат отзывается в той же транзакции. Пользователь видит и изменяет только свои сертификаты. Администратор может работать со всеми сертификатами. Публичный подписанный CRL доступен на `https://portal.example.net/crl/CA-ID`; для включения URL в выдаваемые сертификаты задайте `--portal-url`. NAS/внешняя PKI должны сами проверять CRL; добавление URL не включает такую проверку автоматически.

CRL действует сутки и формируется при запросе. OCSP, подчинённые CA, автоматическое удаление/ротация корневого CA и экспорт его закрытого ключа пока не реализованы. Для ротации создайте новый CA, разверните доверие к нему и перевыпустите клиентские сертификаты; старый CA сохраняется для проверки старых цепочек и CRL.

### ACME-клиент

Настройте ACME в административной панели: публичный домен, контактная почта, HTTPS Directory URL выбранного CA и принятие его условий. Сначала используйте staging directory, например `https://acme-staging-v02.api.letsencrypt.org/directory`; production endpoint по умолчанию — Let’s Encrypt.

Публичные DNS-записи должны указывать на сервер; TCP 80 должен достигать `--acme-http`. Можно запустить `--acme-http :80` с соответствующими правами или пробросить 80 на 8080. Встроенный HTTP-слушатель обслуживает ACME, пользовательские страницы остаются на HTTPS. Внешний HTTPS-порт направьте на нужный TLS-слушатель. Сертификат запрашивается при подключении с SNI настроенного домена и затем автоматически продлевается библиотекой `autocert`; первоначальная выдача может потребовать повторного подключения. Bootstrap-сертификат остаётся резервным для других имён.

ACME-аккаунт и кэш сертификатов/ключей шифруются в БД. ACME здесь — **клиент внешнего CA**, отдельного ACME-сервера для выдачи сертификатов произвольным ACME-клиентам пока нет. Wildcard/DNS-01 не поддерживаются. Проверка настоящего выпуска требует вашего домена и сетевой доступности; локальные тесты не подтверждают выдачу публичным CA.

## Восстановление и эксплуатация

```sh
./bin/radiusd reset-admin-password admin
./bin/radiusd --help
./bin/radiusd serve --help
```

`gen-certs` создаёт ECDSA CA, HTTPS-сертификат для `--host` и административный клиентский сертификат. Он отказывается перезаписывать существующие файлы. Серверный сертификат также используется EAP-TLS; клиентские EAP-сертификаты выпускаются через управляемую PKI в панели/личном кабинете.

Сессии отражают последние сообщения NAS; если Stop потерян, запись может остаться активной. Учёт переданных байтов, восстановление порядка запоздавших событий и полная дедупликация accounting ещё не реализованы. CoA/Disconnect доступны для записанных активных сессий. Журнал пока не имеет автоматической ротации, списки NAS/MAC/VLAN — пагинации. Панель использует защищённую серверную сессию на 30 минут и кнопку выхода; для API также доступен HTTP Basic через HTTPS. mTLS включается отдельно.

RADIUS-пакеты обрабатываются с таймаутом обращения к БД. Неизвестные NAS, неверные подписи и повреждённые пакеты отбрасываются. Ошибка БД не включает изоляцию и не выдаёт доступ. Сервер завершается по SIGINT/SIGTERM с остановкой обработчиков.

## Проверки

```sh
make test
make check
make audit
make build
```

Тесты покрывают MAB, VLAN, изоляцию, MAC-форматы, проверки RADIUS-подписей, accounting, UDP, PKI, авторизацию панели, CSRF и ограничения ссылок на VLAN. CI запускает `-race`, независимый eapol_test, PostgreSQL, миграцию данных и govulncheck; собирает Linux-бинарник как артефакт workflow. Локально PostgreSQL-тесты пропускаются без отдельных тестовых БД в `BORDER_TEST_POSTGRES` и `BORDER_TEST_TRANSFER`. Эти БД должны быть пустыми; тесты сохраняют в них данные.

## Структура

- `cmd/radiusd` — CLI и запуск сервисов.
- `internal/aaa` — Go RADIUS-сервер, пул обработчиков, политики и CoA/Disconnect.
- `internal/eap` — EAP-TLS, состояния и фрагментация, адаптер стандартного Go TLS.
- `internal/store` — SQL-хранилище, миграции и перенос БД.
- `internal/pki` — bootstrap, управляемые CA/сертификаты/CRL, ACME.
- `internal/auth` — зашифрованные TOTP, резервные и почтовые коды.
- `internal/directory` и `internal/mail` — LDAPS/StartTLS и SMTP TLS.
- `internal/selfservice` — отдельный пользовательский HTTPS-портал.
- `internal/web` — защищённый API и встроенная панель на HTML/CSS/JavaScript.
